# HVE Core Codex Porting Notes

This repository is a downstream Codex packaging port of upstream HVE Core. It is
structured to make upstream refreshes deterministic and reviewable.

## Source Of Truth

The canonical upstream source is `microsoft/hve-core`. This port syncs from the
generated upstream bundle at:

```text
plugins/hve-core-all
```

That upstream bundle already normalizes source artifacts into plugin-oriented
directories:

| Upstream source | Upstream bundle | Codex port |
|---|---|---|
| `.github/agents/**/*.agent.md` | `plugins/hve-core-all/agents/**/*.md` | `plugins/hve-core-codex/agents/**/*.md` |
| `.github/prompts/**/*.prompt.md` | `plugins/hve-core-all/commands/**/*.md` | `plugins/hve-core-codex/commands/**/*.md` |
| `.github/instructions/**/*.instructions.md` | `plugins/hve-core-all/instructions/**/*.md` | `plugins/hve-core-codex/instructions/**/*.md` |
| `.github/skills/**/SKILL.md` | `plugins/hve-core-all/skills/**/SKILL.md` | `plugins/hve-core-codex/skills/**/SKILL.md` |

Upstream skills keep their category layout in the Codex port. This preserves
upstream references such as `skills/coding-standards/python-foundational/SKILL.md`
and reduces downstream reconciliation work when upstream adds new skills.

## Overlay Policy

Codex-specific additions live in `overlays/hve-core-codex/`. The sync script
copies overlays into the plugin after upstream files are copied. This keeps local
helper commands, wrapper skills, and route maps separate from upstream content
and avoids editing generated files directly.

## Runtime Surface Policy

This port is runtime-first for upstream commands and agents:

* `plugins/hve-core-codex/commands/` is preserved as the plugin slash-command
  surface where Codex supports plugin commands.
* `plugins/hve-core-codex/agents/` is preserved as the plugin agent-definition
  surface where Codex supports plugin agents.
* Wrapper skills remain the reliable discovery and fallback layer because Codex
  skill discovery is the surface this port can verify consistently.

This repository verifies that wrapper skills are present in the plugin payload.
Runtime testing should also confirm local marketplace cache state: after the
plugin is installed through the Codex UI, `codex exec` and
`codex debug prompt-input` should expose plugin skills with names such as
`hve-core-codex:hve-core-workflows`. If a new wrapper is missing, refresh the
local plugin installation or use direct file references to the wrapper
`SKILL.md` files until the cache is rebuilt.

Upstream agent files are not treated as dynamic Codex `spawn_agent` roles. If a
workflow benefits from Codex subagents, use only the built-in roles exposed by
the current runtime and pass the relevant HVE agent guidance as prompt context.

`scripts/generate-codex-agents.js` also creates optional Codex custom-agent TOML
under `plugins/hve-core-codex/generated/codex-agents/`. Those TOML files are
generated package artifacts, not active Codex custom agents. Users must install
them explicitly into `.codex/agents/` or `~/.codex/agents/` with
`scripts/install-codex-agents.sh`.

`scripts/audit-runtime-surfaces.js` verifies command metadata, agent metadata,
and command-to-agent references as part of `scripts/verify-port.sh`.
`scripts/generate-codex-agents.js --check` verifies generated custom-agent TOML
and manifest freshness as part of `scripts/verify-port.sh`.

## Version Policy

`upstream.lock.json` records the exact upstream HVE Core version and commit. The
Codex plugin manifest may either match the upstream version or add a downstream
suffix in the form `<upstream-version>-codex.N`. Use the suffix when this port
adds wrapper skills, metadata, or compatibility changes without a new upstream
release, because Codex caches installed local plugins by version.

## Wrapper Skill Policy

Curated wrapper skills live under `overlays/hve-core-codex/skills/`:

* `hve-core-workflows`
* `hve-security-workflows`
* `hve-pr-workflows`
* `hve-github-automation`
* `hve-port-maintainer`
* `hve-copilot-instructions`
* `hve-codex-agent-porting`

Each wrapper keeps its `SKILL.md` body short and stores workflow-to-file mapping
in a `references/` route file. Update route references when upstream adds a
user-facing command or agent that should be discoverable through skills. Do not
duplicate upstream command or agent instructions in wrapper skill bodies.

Route maps must use plugin-root-relative paths such as
`commands/hve-core/rpi.md`, not repository layout paths such as
`plugins/hve-core-codex/commands/hve-core/rpi.md`. Wrapper `SKILL.md` files must
tell Codex to resolve those paths from the installed plugin root by moving two
directories up from the wrapper skill directory.

## Generated Codex Custom Agents

Generated custom-agent TOML is built from
`plugins/hve-core-codex/agents/**/*.md` during each upstream sync. The generator
uses path-derived names such as `hve_hve_core_task_researcher` to avoid display
name collisions. It writes a deterministic `manifest.json` with source paths,
generated names, observed frontmatter keys, and install profiles.

When upstream adds or changes an agent:

1. Run `./scripts/sync-upstream.sh ../hve-core`.
2. Confirm the packaged agent markdown has `name` and `description`.
3. Confirm `plugins/hve-core-codex/generated/codex-agents/manifest.json`
   includes the source path.
4. Confirm generated TOML has source metadata and compatibility notes.
5. If generation fails on an unknown frontmatter key, update the generator with
   an explicit mapping or advisory-only decision.
6. Decide whether the agent belongs in an install profile: `core`, `review`,
   `security`, `automation`, or `all`.
7. Decide whether wrapper route maps need user-facing route changes.
8. Run `./scripts/verify-port.sh`.

Do not hand-edit generated TOML for durable changes, do not add an undocumented
`agents` field to `.codex-plugin/plugin.json`, and do not silently write to
`~/.codex/agents/`.

## Exclusions

`owasp-docker` is excluded because upstream marks it as removed due
distribution-incompatible source licensing.

The upstream `installer` skill collection, including `hve-core-installer`, is
excluded because it documents upstream VS Code and GitHub Copilot installation
flows for adding HVE Core assets to another repository. The Codex port provides
its own plugin installation and wrapper skill entrypoints, so shipping the
upstream installer skill would surface misleading setup instructions to Codex
users.

Co-located tests, Python caches, and local tool caches are excluded from the
runtime plugin payload.

## GitHub Agentic Workflow Boundary

Upstream HVE Core includes GitHub Agentic Workflow markdown and compiled lock
files. Those workflows depend on GitHub Actions, GitHub Agentic Workflows,
GitHub Copilot runtime secrets, safe-output tooling, and repository permissions.

The Codex plugin does not enable that automation by itself. Instead, this port
packages the workflows under `github-actions/workflows/` and the source
`.github` artifacts those workflows import under `github-actions/artifacts/`.
Consumer repositories can opt in explicitly after reviewing permissions, write
capabilities, and whether the upstream HVE workflow assumptions fit the target
repository.

## Refresh Workflow

1. Update or fetch the upstream HVE Core checkout.
2. Run `./scripts/sync-upstream.sh ../hve-core`.
3. Run `./scripts/verify-port.sh`.
4. Review the generated diff.
5. Review new or removed files under `plugins/hve-core-codex/commands/` and
   `plugins/hve-core-codex/agents/`.
6. Review generated custom-agent TOML and `manifest.json` changes under
   `plugins/hve-core-codex/generated/codex-agents/`.
7. Update install profiles or wrapper route maps only for intentionally
   user-facing workflows.
8. Update the plugin manifest version if the upstream version changed or if a
   Codex-only change needs a new downstream suffix.
9. Commit the sync with the updated `upstream.lock.json`.
